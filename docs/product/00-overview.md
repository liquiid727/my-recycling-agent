# 城市 AI 骑行计划 Agent 总览

版本：v0.1  
更新时间：2026-05-31  
状态：草稿

## 1. 项目定位

这是一个面向城市周末和节假日休闲骑行用户、采用“通用决策框架 + 城市策略层”的 AI 骑行计划 Agent。

用户不一定是专业训练骑手，而是有骑行意愿、希望用半天或一天完成近距离出行的人。产品要让用户只需要简单询问，并选择或提供出发地点，就能快速知道本次适不适合骑、去哪骑、怎么骑、需要注意什么。

杭州是当前 MVP 的默认城市和首个样板城市，因为当前用户在杭州，且杭州具备丰富的城市绿道、江边骑行、湖区休闲和近郊爬坡场景。长期产品不限定在杭州，而是通过城市策略层复制到其他城市。

用户输入一句话需求，系统输出：

- 推荐路线
- 备选路线
- 风险评估
- 解释型路书

产品第一阶段以 Web 端跑通闭环，后续再迁移到微信小程序。

## 2. 要解决的问题

当前城市休闲骑行用户在出发前通常要自己分散完成多件事：

- 想路线：周末去哪骑、距离够不够、风景好不好
- 定起点：从哪里出发、是否能从家附近直接开始骑
- 查天气：下不下雨、风大不大、体感适不适合骑
- 判风险：坡多不多、补给够不够、返程累不累、车流安不安全
- 排节奏：几点出门、骑多久、哪里休息、骑完怎么收尾

这些决策链路分散在地图、天气 App、社交平台和骑友经验里，信息碎片化，导致用户常见痛点是：

- 有骑行意愿，但无法快速做出出行决策
- 附近周边游玩时，公共交通和骑车的时间差距不大，但骑行方案更需要提前判断
- 能找到路线，但不知道本次是否适合骑
- 能查天气，但无法把天气和路线条件联合判断
- 能做计划，但缺少可解释、可执行的出行方案

## 3. 为什么这个需求成立

这是一个典型的高频轻决策 + 中风险线下活动场景，具备明显的产品切入价值：

- 骑行人群周末决策稳定重复，存在持续需求
- 出发前的决策成本高于执行成本，用户愿意为“省脑力”买单
- 风险判断对体验影响很大，错误建议会直接降低信任
- 输出结果天然适合做可解释推荐，而不是单点信息查询

对用户来说，这不是“查一条路线”，而是“帮我判断这次值不值得骑、骑哪条更合适”。

## 4. 总体能力地图

产品完整能力由三层组成：

### 4.1 A. 路线生成

根据用户输入条件生成多个候选方案。

核心输入：

- 城市
- 出发点
- 可骑时间或目标距离
- 体力等级
- 骑行风格偏好

核心输出：

- 多条候选路线
- 路线长度、爬升、预计时长
- 路线标签，如休闲、刷圈、爬坡、看风景

### 4.2 B. 风险评估

对候选路线做可解释的风险判断。

核心评估维度：

- 天气
- 风向与风速
- 温度与降雨概率
- 坡度与爬升密度
- 车流与道路类型
- 补给可达性
- 返程难度

核心输出：

- 路线风险分
- 风险等级
- 风险原因说明
- 规避建议

### 4.3 C. 完整决策

把路线生成和风险评估整合为最终建议。

核心输出：

- 去不去的建议
- 本次最优路线
- 备选路线
- 推荐理由
- 时间节奏建议
- 骑完后的延展建议，如返程、补给、附近休闲点

## 5. 产品策略

### 5.1 样板城市策略

杭州适合作为首个样板城市，原因在于：

- 城市内兼具城市绿道、湖滨休闲、江边长距离和周边爬坡场景
- 本地骑行文化相对成熟，用户对路线推荐和风险判断有明确需求
- 骑行场景丰富，适合验证“城市策略层”的价值

### 5.2 通用框架 + 城市策略层

产品不做成“杭州专属工具”，而是分两层：

- 通用框架层：输入理解、候选生成、风险评估、解释生成
- 城市策略层：每个城市自己的路线库、地理分区、补给点经验、季节性规则、热门出发点与典型玩法

这样后续可以从杭州复制到上海、成都、深圳等城市。

## 6. 目标用户

优先用户：

- 城市周末骑行新手
- 有一定经验但不想每次手动做规划的骑行用户
- 想要半日游 / 一日游骑行方案的轻度户外用户

不优先的用户：

- 竞赛训练型重度骑手
- 山地越野和极限骑行用户
- 对精确运动数据分析要求极高的专业用户

## 7. 版本切分

### 7.1 总体目标

完整产品覆盖 A + B + C：

- 先解决“能不能生成靠谱路线”
- 再解决“能不能判断这次适不适合骑”
- 最终解决“能不能直接给出整套出行决策”

### 7.2 MVP 目标

MVP 不只做 A，而是做一个可承接 A+B+C 的第一版：

- A 作为主能力，保证候选路线可生成
- B 作为必要判断层，先用规则 + 数据做基础风险评估
- C 作为交付层，输出推荐路线、备选方案和解释型路书

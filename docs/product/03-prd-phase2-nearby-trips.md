# Phase 2 周边游增强 PRD

版本：v0.2  
更新时间：2026-06-02  
状态：mvp2 分支实现中

> 口径说明：新的 MVP01 已经吸收“周末 / 节假日 2 到 3 天附近骑行出行”的产品语义。当前工程里的 `planning_mode=nearby_trip` 仍作为周边出行实现模式保留，但后续需要扩展到多天、住宿、装备和天气窗口。

## 0. 工程隔离约定

Phase 2 周边游能力在工程中以 `planning_mode=nearby_trip` 隔离；已有 Phase 1 路线规划保留为 `planning_mode=route`，即 mvp1 内容。

- mvp1：回答“这次骑哪条路线”，输出主路线、备选路线、天气风险、路书和路线详情。
- mvp2：回答“用骑行完成一次半日 / 一日周边出行”，输出主周边游方案、备选方案、目的地停留、节奏安排、返程和撤退方案。
- 两者复用同一个 `RidePlanningOrchestrator`、天气、风险和审计基础设施，但数据模板、前端模式入口和结果渲染保持显式区分。

## 1. Phase 2 定位

Phase 2 在 Phase 1 单次骑行决策闭环之上，增强“周边半日游 / 一日游”能力。

它不是完整旅游平台，也不是复杂行程规划器。它仍然服务骑行用户，只是把输出从“骑哪条路线”扩展到“用骑行完成一次可执行的周边出行安排”。

## 2. 用户问题

目标用户在周末或节假日常遇到的问题是：

- 附近周边游玩点公共交通和骑车耗时差距不大，但不知道骑车是否更值得
- 想骑车出门，但不想只刷路线，希望有目的地、休息点和返程安排
- 可以接受半天或一天骑行，但不想自己查景点、补给、吃饭、天气和返程风险
- 出发地点不同，适合的周边方向差异很大，通用攻略不能直接使用

## 3. Phase 2 MVP 目标

Phase 2 MVP 要验证：

**用户是否愿意把工具从“路线推荐”升级为“周边骑行出行计划”。**

用户完成一次输入后，应得到：

- 1 个主推荐周边游方案
- 1 到 2 个备选方案
- 骑行路线与目的地节奏
- 天气、强度、拥挤、返程风险说明
- 到达后的停留建议
- 缩短、撤退或公共交通返程方案
- 与 mvp1 一致的三种路线交付：高德 App 导航链接、App 内置路线详情、骑行路线 App / GPX 兼容资产

## 4. 输入范围

Phase 2 的输入必须包含或补齐：

- 城市
- 出发地点或出发区域
- 可用时间：半天 / 一天 / 具体小时数
- 出行日期：周末、节假日或指定日期
- 骑行偏好：休闲、风景、轻爬坡、亲水、古镇 / 公园 / 咖啡等目的地偏好
- 体力等级与爬坡接受度

缺少城市或出发地点时，系统必须先澄清。MVP 默认城市仍可为杭州，但出发地点不能默认。

## 5. 输出结构

### 5.1 主推荐方案

主推荐应包含：

- 方案名称
- 适合人群
- 总骑行距离、预计骑行时长、预计总出行时长
- 推荐出发时间
- 目的地和停留建议
- 为什么推荐
- 本次风险等级

### 5.2 节奏安排

节奏安排按时间段输出：

- 出发前准备
- 去程骑行
- 中途补给或休息
- 到达目的地后的停留
- 返程方式：骑回、缩短骑回、公共交通返程

### 5.3 风险与替代

必须前置说明：

- 天气风险
- 热度 / 拥挤风险
- 爬坡或体力风险
- 返程风险
- 不能按原计划执行时的替代方案

### 5.4 路线交付

Phase 2 的周边游方案不能只输出目的地和时间安排，也必须让用户能执行骑行路线。路线交付沿用 mvp1 的三轨结构：

- 高德 App 导航链接：为去程、返程或缩短路线生成可快速打开的高德骑行导航入口。高德链接用于执行起终点导航，不作为经典骑行路线事实源。
- App 内置路线详情：展示主路线、备选路线、目的地停留、补给点、撤退点、公共交通返程和风险解释，是周边游结果的主要可信交付。
- 骑行路线 App / GPX 兼容资产：保存路线点位、轨迹摘要和方案编号，后续支持 GPX 导出或分享给行者、黑鸟、Strava、Komoot、Ride with GPS 等专业路线工具。

如果高德链接不可用，周边游方案仍应保留内置路线详情和撤退 / 返程说明；如果轨迹资产不足，必须明确标注“当前仅提供关键点路线”。

## 6. Phase 2 MVP 功能清单

### 6.1 用户端必须做

- 周边游模式入口
- 城市和出发地点选择
- 半天 / 一天时间选择
- 目的地偏好选择
- 周边游结果页
- 节奏安排展示
- 返程和撤退方案展示
- 高德 App 导航入口
- 内置路线详情和路线关键点展示
- 路线资产导出或分享入口的结构预留

### 6.2 后台必须做

- 周边目的地模板维护
- 路线模板与目的地模板关联
- 目的地停留建议维护
- 返程方式配置
- 节假日拥挤风险规则
- 周边游查询日志记录
- 周边游方案的去程、返程、缩短路线和撤退路线资产维护
- 高德导航链接生成字段和外部路线资产字段校验

### 6.3 可以后做

- 预算精算
- 门票、营业时间实时校验
- 商家合作推荐
- 多人同行偏好
- 复杂换乘规划

## 8. Agent 与决策链路增量

Phase 2 继续沿用 Phase 1 的编排模型：

```text
User Query
  -> RidePlanningOrchestrator
    -> QueryParserAgent
    -> RoutePlanner
    -> RiskEvaluator
    -> DecisionEngine
    -> RoadbookGeneratorAgent
  -> API Response
```

增量不引入新的自由 Agent，而是在确定性模块中扩展能力：

- `QueryParserAgent`：增加目的地偏好、半天 / 一天、返程偏好的解析字段
- `RoutePlanner`：同时筛选路线模板和周边目的地模板
- `RiskEvaluator`：增加目的地拥挤、返程便利性、总时长超限风险
- `DecisionEngine`：从路线推荐升级为 trip 推荐，但排序仍保持确定性
- `RoadbookGeneratorAgent`：把结构化 trip 结果组织成周边游计划，不得虚构目的地事实

路线交付仍由确定性数据和 provider 产出：`RoutePlanner` 负责路线模板、关键点、外部导航链接和路线资产摘要；`RoadbookGeneratorAgent` 只解释这些结构化事实，不生成不存在的高德链接、轨迹点或第三方路线 App 数据。

## 9. 杭州 Phase 2 样板方向

杭州作为 Phase 2 样板城市时，优先覆盖：

- 湘湖半日休闲骑
- 钱塘江沿线亲水骑 + 咖啡 / 江边休息
- 西湖外围早骑 + 早餐 / 咖啡
- 龙井轻爬坡 + 茶村停留
- 良渚 / 余杭方向半日或一日轻郊游

每个方向都应有明确的出发区域适配范围，不能做成全城统一推荐。

## 10. 成功标准

### 定性标准

- 用户觉得结果像“一次能直接执行的周边出行计划”
- 方案不是景点列表，而是围绕骑行节奏组织
- 风险和返程提示清楚，用户知道什么时候该缩短或改公共交通

### 定量标准

- 每次查询至少返回 1 个可执行主方案
- 80% 以上结果能给出明确返程方案
- 90% 以上结果能给出天气或拥挤风险提示
- 用户从输入到看到主方案的链路不超过一次必要澄清

## 11. 非目标

Phase 2 MVP 不做：

- 多日旅行
- 酒店住宿
- 复杂预算规划
- 实时票务和营业状态保证
- 旅游社区内容生产
- 商业化推荐排序
